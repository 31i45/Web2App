# Skill 01 · 定义 + 设计

> 写代码前把方向和结构钉死。合并了原「定义」和「设计」两阶段——它们是连续思维，分开易断档。
> 本阶段产出可计数的清单，不追求文档华丽。

## 精简版（小项目）

小项目（功能 ≤3、单人用）只做：A1 问题陈述、A2 硬约束、A4 非目标。其余按需。

## 触发条件

- 新项目开始前
- 重大功能新增前
- 需求/架构变更时

## 目标

产出一份「项目合同 + 架构草图」，回答：
1. 做什么、不做什么、怎么算成功
2. 模块怎么分、依赖怎么流、平台差异怎么隔
3. 有什么风险和威胁

## 强制清单

### A. 定义部分

#### A1. 一句话问题陈述（≤30 字）

格式：`为[谁]解决[什么问题]，通过[什么方式]，达到[什么效果]。`

**验收**：说清「谁+问题+方式+效果」，不是「做一个 XX 工具」。

#### A2. 硬约束清单

每条是「必须」或「禁止」，可验证（有对应测试/命令）。

| 类别 | 必须 | 禁止 | 验证方式 |
|---|---|---|---|
| 体积 | | | |
| 平台 | | | |
| 安全 | | | |
| 依赖 | | | |

**验收**：无「尽量」「最好」。每条可验证。

#### A3. 成功标准（可测量）

格式：`指标 比较符 数值`。如 `产物 < 1 MiB`、`测试 ≥ 80`。

**验收**：无「轻量」「快速」等模糊词。每条有验证方法。

#### A4. 非目标清单（≥3 条）

明确「不做什么」，防范围蔓延。如：不做系统托盘、不做离线资源包、不做某操作系统。

**验收**：≥3 条。是「不做」不是「以后做」。

#### A5. 风险假设（3 个）

| 风险 | 验证方式 | 缓解措施 |
|---|---|---|

**验收**：3 个各不相同，有具体验证方式。

---

### 定义完成门 ⛔

A1-A5 全部验收通过后，才能开始 B 部分。定义是设计的前提，没定义清楚的设计必然返工。

**检查**：
- [ ] A1 ≤30 字且说清谁+问题+方式+效果
- [ ] A2 每条可验证
- [ ] A3 每条可测量
- [ ] A4 ≥3 条非目标
- [ ] A5 3 个风险有验证方式

全部打勾才能进入 B。

---

### B. 设计部分

#### B1. 模块边界图

画出模块依赖，箭头单向无环。低层不依赖高层。

**验收**：无循环依赖。每个模块职责一句话说清。

#### B2. 深模块判定

深模块 = 接口承载复杂度，调用方心智负担低。判定标准：**调用方使用本模块需要写几行代码**（越少越深）。公开项数仅作参考。

| 模块 | 调用方代码行数 | 深度（深/浅） | 理由 |
|---|---|---|---|

浅模块必须有存在理由（平台接缝、隔离依赖），否则合并。

**验收**：核心模块调用方代码 ≤5 行。浅模块有明确理由。

#### B3. 接缝设计

平台差异收敛到唯一的接缝模块：接缝内各平台实现同名同签名，接缝外上层代码零平台分支。接缝的具体机制（条件编译/接口/适配器等）是项目级决策，记录到 ADR。

**验收**：上层代码零平台分支。各平台实现签名一致。接缝机制有 ADR。

#### B4. 依赖最小化

每个直接依赖回答「为什么需要」。决策树：需要吗？→ 标准库能做吗？→ 手写成本 < 依赖成本吗？

| 依赖 | 理由 | 传递依赖数 |
|---|---|---|

**验收**：能用标准库不用第三方包。能手写的不引入（仅限协议/编码等小而关键部分）。

#### B5. STRIDE 威胁建模（设计级）

对每个数据流问一句「这里可能怎么被滥用」，按 STRIDE 分类。**只填有实际威胁的类别，N/A 不填。**

| 数据流 | 威胁类别 | 具体场景 | 设计级缓解 |
|---|---|---|---|

STRIDE 六类：Spoofing/Tampering/Repudiation/Info Disclosure/DoS/Elevation。

**验收**：每个数据流至少过一遍。无缓解的威胁标注严重度。不强迫填满六类。

## 验收标准

- A1-A5 + B1-B5 全部完成
- 问题陈述 ≤30 字
- 非目标 ≥3 条
- 模块边界无环
- 核心模块是深模块
- 平台差异收敛在接缝内
- 每个依赖有理由
- STRIDE 有产出

## 反证记录

- **定义和设计合并会不会太胖？** → 约 12KB，但定义和设计是连续思维，分开易断档。加了定义完成门防止跳步。
- **定义完成门会不会变成形式主义？** → 门有具体检查项（A1≤30字等），不是「你觉得清楚了吗」。
- **STRIDE N/A 不填会不会遗漏威胁？** → 要求「每个数据流至少过一遍」，过了才决定填不填。核心是过一遍思维，不是填表。
- **深模块用调用方行数会不会不准？** → 比公开项数准。公开项少但参数多，调用方行数仍多。调用方行数直接反映心智负担。
- **接缝机制不定死（条件编译 vs 接口）会不会失去指导性？** → 指导性在不变量：接缝唯一、同名同签名、上层零平台分支。机制是项目决策，被第二个平台实现逼出时自然定型。
- **精简版会不会让复杂项目走精简？** → 精简版明确适用「功能≤3、单人用」。超出范围必须全量。
