# Skill 03 · 验证 + 维护

> 合并了原「验证」和「维护」两阶段——验证完立即维护，文档不会忘。
> 本阶段目标：真机可用 + 文档不腐烂 + 决策可追溯。

## 精简版（小项目）

小项目只做：A1 真机验证、A2 文档数字校验、B1 文档预算。其余按需。

## 触发条件

- Skill 02 完成后
- 每次发布前
- **大版本发布前必做半年审计**（替代「每 6 个月」，强制触发）

## 强制清单

### A. 验证部分

#### A1. 真机全平台验证

对项目支持的每个目标平台逐一真机验证。场景与命令取自项目实例文件（INSTANCE.md），至少覆盖：

| 场景 | 平台 A | 平台 B |
|---|---|---|
| 工具启动 | | |
| 核心功能执行（典型输入） | | |
| 核心功能执行（含自定义资源） | | |
| 产物运行 | | |
| 退出零残留 | | |
| 重复执行（幂等） | | |
| 无效输入不可误运行 | | |

必须真实机器，不能只用 CI。

**验收**：全平台 e2e 全绿。人工抽检 2-3 个真实使用场景。只跑了部分平台时必须显式标注「半」，不得视为全绿——缺的平台是显性待办，不是可忽略项。

#### A2. 文档数字 CI 校验

CI 中比对 README 声明值与实际值。**用「≤」或区间非「==」**——优化让体积变小不触发失败，变差（超过红线）才失败。版本号是唯一等值例外（见下行）。

| 数字 | 校验方式 | 比较符 |
|---|---|---|
| 产物体积 | 构建后比对 | ≤ 红线（值见实例文件） |
| 测试数 | 测试命令输出比对 | ≥ 目标 |
| 端到端断言数 | e2e 输出比对 | ≥ 目标 |
| 版本号 | 发布 tag == 代码内版本声明 == 产物元数据 | ==（版本漂移无「变好」方向，等值才是正确语义） |

**验收**：CI 有此 step。数字变更时代码+文档同 commit。优化（数字变好）自动通过，劣化（数字变差）失败。

#### A3. 违禁词扫描

内部术语不出现在对外文档。违禁项分两级，清单在项目实例文件（可独立成文，附寿命标签，见 B2）：

- **词级**：具体术语原词。CI grep 扫描 README/Release Notes，引用清单文件而非硬编码。
- **概念级**：未用原词、但描述了内部特色本身的段落。CI 扫不出来，发布前人工对照清单逐条问「对外文档是否描述了这一条」，核对有记录。

清单只收录已确认的内部特色，不开放式发散审读全文（防误报）。

**验收**：CI 有词级扫描 step（引用实例文件）。概念级人工核对有记录。对外文档无清单内术语、无清单内概念的描述。

#### A4. 核心不变量机械断言

对架构最关键的不变量做字节级/结构级自动化断言，不依赖人工比对。断言清单取自项目实例文件，至少覆盖三类：

- 派生不变量：产物确实派生自声明的源
- 幂等不变量：重复操作不改变结果、不膨胀
- 局部性不变量：局部变更只影响预期区段

**验收**：不变量断言全通过。

#### A5. 环境差异排查

| 维度 | 检查项 |
|---|---|
| OS 版本/发行版 | 项目支持的版本清单（实例文件） |
| 运行时/引擎版本 | 平台 Web 引擎与运行时实际版本 |
| 系统配置 | 区域、DPI、显卡 |
| 安全软件 | 系统安全策略与拦截规则 |
| 权限 | 管理员/普通用户 |

**验收**：有排查清单。真机问题 30 分钟内定位环境或代码。

---

### B. 维护部分

#### B1. 文档预算

| 文档类型 | 预算（每 1000 行代码） |
|---|---|
| 核心文档（README+构建指南） | 不限 |
| 设计文档 | ≤300 行 |
| 评审/分析报告 | ≤200 行 |
| 术语表 | ≤30 条 |

**验收**：文档量在预算内。超预算有删除/合并计划。

#### B2. 文档寿命标签

每份非 README 文档顶部标注：
```markdown
> 有效期：XX 变更时需更新
> 最后验证：YYYY-MM-DD（commit xxx）
```

**验收**：非 README 文档有寿命标签。超 6 个月未验证的复核或删除。

#### B3. 架构决策记录（ADR）

满足以下**任一触发条件**的决策必须写 ADR：

- 新增/移除依赖
- 架构变更（模块拆分/合并）
- 放弃某个方案（为什么不选）
- 安全相关决策
- 违反直觉的决策（为什么不用常规做法）

ADR 格式：

```markdown
# ADR-00X: 标题
## 状态：已采纳/已废弃/已替代
## 背景
## 决策
## 后果（好/坏）
## 替代方案
```

**验收**：触发条件清单内的决策都有 ADR。废弃 ADR 不删除，标注状态。

#### B4. 半年审计（绑定大版本发布）

**强制触发：大版本（如 v2.0→v3.0）发布前必做。** 小版本按需。

- [ ] 文档量超预算？
- [ ] 寿命标签准确？
- [ ] 时点快照需更新/删除？
- [ ] ADR 状态需更新？
- [ ] README 数字一致？
- [ ] 术语表冗余？
- [ ] 经验已沉淀到实例文件？方法论本身有需修订处？

**验收**：审计有记录。过时文档被处理。经验沉淀到实例文件（B5）。

#### B5. 经验沉淀

本次学到什么？实例与教训沉淀到项目实例文件（INSTANCE.md）。skills 本体保持通用——只有经验证明「方法论本身有缺陷」时才修订 skills，且修订只改通用规则、不写入项目实例。

**验收**：经验有沉淀记录（实例文件）。skills 若有修订，每处改动可追溯到方法论缺陷而非项目个例。

## 验收标准

- A1-A5 + B1-B5 全部完成
- 全平台真机 e2e 全绿
- CI 有文档数字校验
- 核心不变量断言通过
- 文档量在预算内
- 重要决策有 ADR
- 半年审计有记录

## 反证记录

- **验证和维护合并会不会让维护被忽略？** → 不会。A 验证完立刻做 B 维护，文档不会忘。分开的话维护容易被跳过。
- **文档预算会不会删该有的文档？** → 预算是上限不是目标。核心文档不限。超预算说明代码复杂度超单人维护能力，应拆项目而非加文档。
- **ADR 触发条件会不会太宽松导致 ADR 泛滥？** → 5 个触发条件是硬阈值，不满足的不写。判断标准是「6 个月后会不会有人问为什么」。
- **半年审计绑定大版本会不会让小版本积累问题？** → 小版本审计标「按需」，鼓励做但不强制。大版本是强制节点。
- **文档数字用 ≤ 会不会让数字越来越大没人管？** → ≤ 是红线，README 写最大值。代码劣化超过红线才失败，优化自动通过。红线本身由人设定，不是 AI 决定。
- **精简版会不会让项目该做的不做？** → 精简版明确「功能≤3、单人用」范围。超出范围必须全量。小项目省流程，大项目保质量。
- **版本号用 == 会不会违背「用 ≤ 非 ==」原则？** → 该原则针对有优化方向的量（体积变小是变好）。版本漂移没有「变好」方向，tag 与代码版本不一致本身就是错误，等值才是正确语义，是唯一例外。
- **概念级核对是不是主观发散？** → 不是。清单只列已确认的内部特色，逐条问「是否描述了它本身」，是有限次闭合核对，不是开放式审读。
- **单平台标「半」会不会让 A1 永远过不了？** → 「半」不是失败态，是诚实态。它把「缺另一平台真机」从隐性自欺变成显性待办，验收是否通过由人判断，但状态必须真实。
- **实例外移到 INSTANCE.md 会不会让 skills 失去自足性？** → skills 定义实例文件约定（00 原则 6），新项目先建 INSTANCE.md 再走清单。「通用规则 + 实例文件」合起来才是完整可执行清单。
