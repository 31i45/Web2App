# Skill 02 · 实现 + 对抗审计

> 合并了原「实现」和「对抗」两阶段——预埋兜底和攻击审计是一体两面，放一起消除边界模糊。
> 本阶段目标：代码正确 + 故障可控 + 攻击面收敛。

## 精简版（小项目）

小项目（功能 ≤3）只做：A2 规模红线、A4 错误处理、B5 供应链审计。其余按需。

## 触发条件

- Skill 01 完成后
- 每个核心模块完成后
- 发布前全量执行

## 强制清单

### A. 实现部分

#### A1. 测试存在性与质量

TDD 是手段，测试覆盖是目的。不强求红阶段顺序（git 历史不可验证），但要求：

- 每个公开函数 ≥1 测试
- 边界值：0、1、最大值、最大值+1
- 错误路径：每个失败分支有对应测试
- 测试名描述行为（如 `parse_rejects_truncated_frame`）

**验收**：无空断言测试。边界值覆盖。测试失败能直接定位。

#### A2. 规模红线

| 指标 | 红线 | 超线处理 |
|---|---|---|
| 函数行数 | ≤50 | 拆分 |
| 模块公开项 | ≤10 | 拆分 |
| 函数参数 | ≤5 | 打包成结构体/对象 |
| 嵌套层级 | ≤4 | 提前 return |

**验收**：全部满足，或有「为什么必须超」的注释。

#### A3. 注释纪律

注释只解释「为什么」，不解释「是什么」。

**验收**：删除注释后代码仍能读懂→好注释。代码读不懂→重构代码不加注释。

#### A4. 错误处理完整路径

- 每个错误传播点：错误最终在哪处理？
- 每个速断调用（「理论不可能失败」的强制解包/断言类写法）：必须注释「为什么不会失败」，否则改为显式错误处理
- 每个文件/网络/内存操作：失败返回什么？
- 每个主动崩溃点：必须是不可恢复错误+注释

**验收**：速断调用全部有注释（无裸奔）。错误路径有测试。用户可见错误信息可读。

#### A5. 故障路径预埋（本模块只管预埋兜底代码，不管测试；测试在 B 部分）

| 场景 | 兜底措施 | 代码位置 |
|---|---|---|
| 输入格式错误 | 返回明确错误，不崩溃 | 文件:行号 |
| 资源分配失败 | 释放已分配，返回错误 | 文件:行号 |
| 中途操作失败 | 回滚到操作前状态（原子性） | 文件:行号 |
| 进程被强制终止 | 关键状态已持久化或可重建 | 文件:行号 |
| 并发冲突 | 锁/原子/消息队列 | 文件:行号 |

**验收**：核心功能故障路径有兜底代码实现（附文件:行号）。无代码的兜底不算预埋。不允许「先主路径，故障以后再说」。

#### A6. 测试质量（与 A1 合并执行）

A1 要求「有测试」，A6 要求「测试有质量」。合并验收：

- 每测试有明确断言（非「不崩溃」）
- 边界值：0、1、最大值、最大值+1
- 错误路径：每个失败分支有对应测试
- 测试名描述行为（如 `parse_rejects_truncated_frame`）

**验收**：无空断言测试。边界值覆盖。测试失败能直接定位。

---

### B. 对抗审计部分

#### B1. STRIDE 威胁建模（实现级）

对每个外部输入点（用户输入、文件、网络、CLI 参数、环境变量等，清单见项目实例文件）问「这里可能怎么被滥用」，按 STRIDE 分类。**只填有实际威胁的类别，N/A 不填。**

| 输入点 | 威胁类别 | 具体攻击场景 | 防御措施 |
|---|---|---|---|

STRIDE 六类：Spoofing/Tampering/Repudiation/Info Disclosure/DoS/Elevation。

**验收**：每个输入点过一遍。无防御威胁标注严重度。不强迫填满六类。

#### B2. 输入恶意化测试

每个恶意值对应测试用例，断言「不崩溃+合理错误处理」。

| 类别 | 测试值 | 测试名 |
|---|---|---|
| 空值 | "" / null / 缺字段 | |
| 超长 | 远超合理上界的输入 | |
| 路径穿越 | "../" / "\\" / ":" | |
| 控制字符 | \x00 / \n / Unicode 控制符 | |
| 格式错误 | 损坏的结构化输入（坏魔数/错校验和/非法编码） | |
| 重复操作 | 同一产物/资源重复执行（幂等性） | |

**验收**：清单全覆盖。每测试有明确断言。可由测试命令复现。

#### B3. 故障注入清单

对每个核心功能列 5 种故障，标注「兜底：有/无/部分」。

核心功能清单取自项目实例文件。

**验收**：每功能 5 种故障。「无」兜底的高严重度必须补或标注已知风险。

#### B4. 竞态分析

| 共享资源 | 访问点 | 同步机制 | 风险 |
|---|---|---|---|

共享资源：临时文件、全局/配置状态、进程状态、外部资源。

**验收**：共享资源清单完整。无同步的并发访问标注风险。

#### B5. 依赖供应链审计

二选一：

**首选（零安装）**：代码托管平台的依赖漏洞告警（开启即自动监控依赖 CVE）。

**备选（本地/CI）**：
1. 语言生态的漏洞扫描器——具体工具及运行方式见项目实例文件
2. 依赖树清点，设传递依赖数量阈值
3. 每依赖：最近更新时间、维护状态

**验收**：平台漏洞告警开启 或 扫描器无高危。传递依赖数有记录。每直接依赖有理由。

## 反证记录

- **实现和对抗合并会不会太胖？** → 约 14KB，但预埋和审计是一体两面，分开易边界模糊。A5 明确要求附代码行号，防止只测试不预埋。
- **A1 不强求 TDD 红阶段会不会降低质量？** → TDD 红阶段不可观测，强制无意义。改为要求测试存在性+质量，更可验证。
- **5 种故障会不会凑数？** → 要求标注「兜底：有/无」。凑数会导致兜底写「无」，反而暴露风险。
- **平台漏洞告警会不会漏报？** → 会。所以加了传递依赖数量监控和维护状态检查。平台告警是首选因为零安装。
- **STRIDE 实现级和 01 设计级会不会重复？** → 不重复。01 是架构级（数据流有没有根本缺陷），本 skill 是实现级（具体输入的恶意值）。两级互补。
- **注释只解释「为什么」会不会让新人看不懂？** → 代码本身应说明「是什么」。说不清就重构代码。注释补充代码无法表达的决策背景。
