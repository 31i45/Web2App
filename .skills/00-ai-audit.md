# Skill 00 · AI 自我审计（元规则）

> 横切全流程的信任基石。不懂代码的人 + AI 协作，最大风险是 AI 自说自话。
> 本 skill 强制 AI 自我质疑，且产出必须可计数、可验证。

## 横切原则（所有 skill 共享）

1. **二八定理**：每个阶段先做 20% 最重要的，不追求面面俱到。
2. **检查清单定位**：不强调顺序，强调每条必过。可以跳着做，但每条都要打勾。
3. **可计数且具体**：产出必须可数（如「3 个风险」）且具体到可操作（风险格式：`[触发条件]→[后果]→[缓解/已知]`，不接受「可能有 bug」类模糊产出）。
4. **极简主义**：能合并的不拆分，能删的不保留。
5. **小项目精简版**：每个 skill 标注了「精简版」模块，小项目只做核心模块，不强制全量。
6. **通用与实例分离**：skills 只含普适规则。项目专有事实（命令、红线、工具名、平台名、专有清单）一律写入项目实例文件 INSTANCE.md（使用本套 skills 的项目在其 skills 目录提供），skills 只引用不内嵌。

## 触发条件

AI 完成任何产出（代码 / 文档 / 分析 / 方案）后，交付前必须执行。

## 分级执行

按**改动类型**分级，不按量。边界模糊默认 B 类（全 5 条）。

| 类别 | 改动类型 | 执行规则 |
|---|---|---|
| A | 注释、文档措辞、格式、重命名（不改逻辑） | 仅规则 4 + 规则 5 |
| B | 逻辑改动、架构决策、安全相关、依赖变更 | 全 5 条 |

降级必须在产出中显式声明「A 类改动，仅执行规则 4+5」，否则默认全 5 条。

## 强制清单

### 规则 1：反证义务

先尝试证明方案错了，再证明对的。列出 2-3 个具体反例，逐一构造。反例失败→通过；反例成立→否决方案。

**验收**：必须写出「我尝试了 X 反例，结果 Y」，禁止只说「没问题」。

### 规则 2：简化义务

回答「能不能删一半代码/文件/依赖」。删除后测试仍通过→必须删；有更简单替代→采用。

**验收**：必须给出「尝试删除 X，测试结果 Y」。禁止说「必要」而不证明。

### 规则 3：风险声明

列 3 个具体风险，禁止「无风险」。每个风险格式：`[触发条件]→[后果]→[严重度 高/中/低]→[缓解措施或标注"已知风险"]`。

**验收**：3 个风险各不相同且具体可操作。不接受「可能有 bug」「可能慢」类模糊风险。高风险必须有缓解或标注「已知风险」。

### 规则 4：可验证性

每个事实声明必须能用一条命令验证，且附该命令输出中证明声明的那一行摘要。

**验收**：声明后附 `命令` + `输出关键行`。如声明「84 测试通过」，须附项目测试命令 + 输出中形如 `ok. 84 passed` 的关键行。用户能复制命令并对照摘要验证。

### 规则 5：来源标注

事实声明必须给出处：代码→文件:行号；文档→链接；实测→命令+输出。

**验收**：无来源的事实声明视为未通过。禁止编造来源。

## 输出物

交付内容末尾必须附：

```
## 自我审计
- [反证] 尝试了 X 反例，结果 Y
- [简化] 尝试删除 X，结果 Y
- [风险] 1) 触发X→后果Y 严重度Z；2)...；3)...
- [验证] 声明 X 可由 `命令` 验证
- [来源] 声明 X 来源于 文件:行号
```

## 验收标准

5 条全部执行，有具体产出。未通过则修正后重审。

## 反证记录

- **5 条会不会过度质疑拖慢产出？** → 每条有明确产出和验收，反证失败即通过，不循环。
- **用户不懂代码怎么判断反证诚实？** → 规则 4 要求附输出摘要，规则 5 要求来源，用户可对照验证。
- **分级按类型会不会让 AI 把逻辑改动说成 A 类？** → A 类明确定义为「不改逻辑」，逻辑改动归类 B。AI 若撒谎，用户对照改动内容可追责。
- **可计数+具体会不会过度约束产出？** → 只约束格式不约束内容。具体风险比模糊风险更有价值。
- **小项目精简版会不会让 AI 永远走精简？** → 精简版有明确适用范围（小项目），复杂项目必须全量。判断依据是功能数和用户量。
- **通用不内嵌实例会不会让 skills 空洞？** → 实例在 INSTANCE.md，可验证性由「通用规则 + 实例文件」合力承担。skills 保持可迁移，实例保持具体。
